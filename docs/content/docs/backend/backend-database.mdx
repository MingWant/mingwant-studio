# 后端数据库

后端使用 GORM 管理 SQLite 或 PostgreSQL，启动时由 `backend/internal/database/schema.go` 对 `backend/internal/model/models.go` 中登记的模型执行 `AutoMigrate`。数据库只保存业务状态和资源索引；用户侧 API Key 默认位于浏览器账号级会话密钥区，用户明确选择后才持久保存，异步任务执行期间则可能加密进入可信自部署环境。

## 账号与认证会话

`auth_sessions` 只保存随机会话 Token 的 SHA-256 哈希、用户 ID、创建时间和到期时间，不保存可直接用于登录的 Cookie 原文。Cookie 默认有效期为 30 天且不滑动续期。创建新会话、删除全局过期会话和裁剪同一用户的旧会话在一个数据库事务中完成；每个账号最多保留最近 20 个活动会话，新创建会话始终保留。

用户调用“退出其他会话”时按 `user_id` 删除当前会话 ID 之外的记录。管理员修改密码、角色或账号状态时先删除该用户全部会话，删除失败则不继续保存安全变更；普通退出即使服务端删除失败也先让浏览器 Cookie 过期并返回显式错误，便于管理员处置可能残留的哈希记录。

### `email_verification_codes`

验证码表保存邮箱、用途、HMAC-SHA-256 码摘要、`attempts`、`expires_at`、`sent_at`、`used_at` 和创建时间，不保存六位码原文。创建新码时在事务内把同邮箱同用途的旧未消费记录写为已用，再插入 `sent_at = NULL` 的 pending 记录；只有 SMTP 成功后条件更新 `sent_at` 的记录才会进入查询。

错误校验以 `attempts < 5` 为条件原子自增，多实例并发不能突破上限。最终注册事务必须同时匹配记录 ID、用户邮箱、用途、非空 `sent_at`、空 `used_at`、未过期和错误次数上限，然后先消费验证码再创建用户；条件竞争、重放、跨邮箱替换或锁定后的正确码都不能创建第二个账号。

## 模型渠道与模型目录

### `model_channels`

一条记录表示一个系统或用户模型渠道。`interface_type` 是渠道的默认模型协议，负责新模型预填和未覆盖模型的请求方式；`api_format` 表示默认鉴权与报文族，Gemini GenerateContent 与 Gemini Veo 使用 `gemini`，其他当前协议使用 `openai`。

### `channel_models`

一条记录表示渠道下的一个可选模型。关键字段如下：

| 字段 | 作用 |
| --- | --- |
| `channel_id`、`model_key` | 在未软删除记录中联合唯一定位模型 |
| `display_name` | 面向用户的模型名称 |
| `capability` | `text`、`image`、`video` 或 `audio` |
| `protocol` | 模型实际请求协议；为空时继承所属渠道的 `interface_type` |
| `capability_config_json`、`capability_version` | 模型能力约束的服务端事实源及版本；当前视频配置包含提示词、参考媒体、时长、比例、分辨率、音频/水印和生成模式限制 |
| `billing_mode` | `fixed_request` 或 `per_second` |
| `unit_price_microcredits` | 以微积分保存的单价 |
| `price_configured`、`enabled` | 控制定价完整性和模型可见性 |
| `price_version` | 定价变更版本 |
| `probe_status`、`probe_transport` | 最近一次 LLM 测活终态和真实流式方式 |
| `probe_duration_ms`、`probe_checked_at` | 测活耗时与检查时间 |
| `probe_config_hash` | 服务端请求配置指纹；只用于使旧测活结论失效，不通过 API 返回 |
| `tool_probe_status`、`tool_probe_checked_at` | 最近一次固定无副作用 Function Calling 诊断的终态与检查时间 |
| `tool_probe_verifier_version`、`tool_probe_config_hash` | 工具 Schema 校验版本和服务端请求配置指纹；配置变化或校验规则升级后不再复用旧结论 |

`protocol` 当前支持 Chat Completions、OpenAI Responses、Gemini GenerateContent、OpenAI Images、xAI Imagine Images、OpenAI Audio、OpenAI/NewAPI Videos、NewAPI 媒体任务、NewAPI Video Generations、xAI 视频和 Gemini Veo。保存模型时后端会校验协议与 `capability` 是否一致；后台任务以模型协议为最终请求契约，并据此选择鉴权、创建路径、请求体和轮询方式。

视频模型能力配置通过管理端保存为版本化 JSON，前端只负责展示和预填。创建任务时，后端会在预留积分前按系统模型行或自定义请求的能力配置核对提示词长度、参考资源数量/大小/时长、输出时长、比例、分辨率、音频、水印和生成模式；带 `resource:` 身份的资源大小和时长以服务端 `resources` 表为准。没有历史配置的模型按协议安全模板校验，非法配置不能通过保存。

`channel_models` 是启停、协议和定价的唯一事实源，`model_channels.models_json` 仅保留给旧客户端和受限代理作兼容投影。新增或修改渠道、启停/删除模型、更新兼容投影以及因渠道配置变化清空测活状态都在同一事务中提交，并先锁定对应渠道行，避免两个管理员并发留下过期清单。启动迁移只会在该渠道从未存在任何模型行时读取一次旧 JSON；即使全部模型已经软删除，也会把兼容投影修复为空而不会复活历史模型。新任务和同步代理最终都从启用的 `channel_models` 校验模型；只有已经创建上游任务的人工轮询恢复允许读取停用模型的历史协议。

上游目录在进入事务前会限制为 8 MiB 响应、5000 个原始条目和 2000 个去重模型；`model_key`、`display_name` 分别按 120、160 个 Unicode 字符校验，并拒绝控制字符。缺失模型使用 100 条一批的 `ON CONFLICT DO NOTHING` 写入，既保留并发管理员已经完成的定价，也避免单条 SQL 超过 SQLite 或 PostgreSQL 的绑定参数上限。自动发现只创建未启用、未定价的新行，不能绕过管理员确认。

## 短剧项目制作事实

短剧项目继续使用项目表作为唯一事实源，不建立独立 JSON、JSONL 或文件 WAL：

| 模型 | 事实归属 |
| --- | --- |
| `project_units` | 分集/章节正文、逐字台词、顺序和正文修订时间 |
| `asset_versions` | 人物、地点、服装和道具的稳定身份、当前状态及提示词版本 |
| `shots` | 镜头标题、可见描述、时长、状态和结构化制作定义 |
| `shot_asset_references` | 镜头与精确资产版本、首帧、尾帧、关键帧及输出的业务绑定 |
| `workflow_step_instances` | 阶段候选、用户确认、独立审查和交付结论 |

### `shots.definition_json`

`definition_json` 使用 `mingwant.short-drama.shot/v1` 契约，保存原文章节/段落来源、观看目的、信息变化、精确资产版本、开始边界、结束边界、视频运动说明以及图片/视频提示词投影。`duration_ms` 仍是时长唯一权威；运动说明不能覆盖镜头时长或结束边界。

后端对非空结构化定义执行强校验：来源章节必须属于同一项目，资产版本必须存在，开始和结束边界必须包含主体位置，运动动作必须按序提供主体、动作和结果。空对象只用于尚未结构化的普通镜头；前端导入此类镜头时会显示降级警告，不得伪装为可直接生成的结构化镜头。

## 异步任务与计费终态

`tasks` 使用 `lease_owner` / `lease_expires_at` 领取 Worker 租约；`provider_call_state` 是不对客户端公开的供应商调用边界。`pending` 表示新尝试尚未提交调用前检查点；`preflight` 表示有效租约、调用阶段和审计日志已经原子落库，但供应商 HTTP 请求仍未发出；`dispatched` 表示至少一次请求已经跨过本地发送边界，之后即使连接取消也必须按可能执行处理。旧版 `prepared` 与空值没有精确发送证据，只能保守视为可能已经调用。异步视频创建成功后把供应商任务 ID、`poll_stage` 与 `next_poll_at` 持久化，释放 Worker，到了查询时间再重新领取。RunningHub RHWorkspace 还使用私有 `provider_state_json` 保存创建时的控制节点、结果节点证据、结果地址以及取消请求、接受和终态确认；WSS 鉴权地址不得落库。取消接口返回成功只记录“取消已接受”，之后只有同一 taskId 的输出查询进入中断/取消终态，或已接受取消后返回任务已清除，才记录取消终态确认；若先观察到正常完成则必须标记自然结束并拒绝交付。断点模式只有在节点 12 已产出结果，并且 WSS 或结构化失败对象明确指向创建时保存的节点 69 时，才记录工作流断点终止；不能从异常正文猜测节点身份。Worker 中断后只能监控、取消和读取同一个上游 taskId，没有结果节点证据、失败节点不符或已经自然结束的工作流不得恢复为成功。`idx_tasks_status_next_poll` 用于定位到期轮询任务，原始 `started_at` 负责约束跨重启的总超时时间。

画布节点生成、脚本分镜、影视 Agent 会话和 LLM 测活任务还保存不对外返回的 `request_key`。画布键由服务端按任务类型、画布 ID、操作和节点 ID 计算 SHA-256；影视 Agent 任务按持久会话 ID 计算，均不接受浏览器覆盖。自定义渠道探针键包含用户已校验的完整配置摘要，系统探针键只按渠道与模型生成稳定摘要，文本测活和固定工具诊断共用该活动键但在输入中保存不同 `kind`，任何键都不保存 API Key 明文。`idx_tasks_user_active_request_key` 只在 `queued` / `running` 状态下对 `user_id + request_key` 建立部分唯一约束；`idx_tasks_active_system_probe_key` 再对 `probe-system-`（以及早期 `probe-tool-system-`）系统探针键建立跨用户部分唯一约束。探针首次创建时把 Web 请求前生成的随机键保存到私有 `probe_request_key`，`idx_tasks_user_probe_request_key` 对 `user_id + probe_request_key` 做不受任务终态影响的永久唯一约束。

### `channel_probe_submissions`

活动配置互斥可能让当前请求接管另一个标签页或管理员创建的探针，单个任务字段无法保存多个接管者的提交键。本表以 `user_id + submission_key` 永久唯一保存接管映射，并记录不可逆的配置请求键和实际 `task_id`；不保存 API Key、提示词或响应正文。后端必须先写映射再返回接管结果，之后即使该响应丢失且原任务已经进入终态，重发仍会返回同一任务。多标签页、重复点击、脚本直调、多管理员或多实例并发提交同一操作时，不创建第二张任务、计费订单或供应商调用；收到明确响应后的生成重试或重新测活会使用新提交身份进入下一轮。

`sessions.request_key` 保存 Web 为一次影视会话创建生成的随机幂等键，不通过公开响应返回；`idx_sessions_user_request_key` 永久约束同一用户只能有一个对应会话。创建接口遇到响应丢失后可携带原键重发并取回原会话；若进程只写入了会话还没来得及创建任务，固定的首条消息 ID 与会话任务请求键会恢复缺失步骤，仍只产生一张订单。

任务成功、失败和取消都必须以当前状态与租约作为条件原子转移，迟到 Worker 不得覆盖用户取消或其他 Worker 的终态。供应商任务 ID 的回写还需匹配当前 `billing_order_id`、尝试开始时间或持有中的 Worker/人工恢复租约，避免旧尝试的迟到响应污染新重试。`billing_orders` 的结算与退款同样先抢占唯一终态，再在同一事务内更新 `credit_accounts` 与 `credit_ledger_entries`，防止重复扣减或重复归还预留积分。

## 生成资源与交付检查点

`resources` 对普通上传继续只保存对象索引；由后台任务把 Base64 内联媒体落盘时，还会写入不对客户端公开的 `source_task_id`、`source_attempt`、`source_path`、`content_sha256` 与 `quota_day`。`source_attempt` 优先使用当前计费订单 ID，无平台订单时使用当前任务尝试次数；因此人工恢复同一次供应商结果会命中原资源，而用户明确确认的新付费重试不会误拿旧文件。`quota_day` 只用于中断后恢复原 pending 对象时识别已经计入的 UTC 日上传量，避免同一文件恢复一次就重复累计一次。

`idx_resources_task_output` 对 `pending` / `ready` 资源约束 `user_id + source_task_id + source_attempt + source_path` 唯一。服务按“查重、全批额度预留、认领待恢复行、写对象”的顺序执行；中途失败后再次恢复时，只有摘要、大小和 MIME 都一致的 `ready` 资源才允许直接复用。运行中的新鲜 `pending` 会阻止并发覆盖；超过三分钟仍未完成的 pending 必须先以数据库条件更新抢占，已经取得终止任务人工恢复租约的“恢复已保存结果”可以立即抢占，再用原对象键和同一正文重写，其他 Worker 不能同时恢复。同路径不同正文始终拒绝。账号已存文件总量只统计 `ready` 资源与会话附件，失败或未完成的资源行不会永久吃掉可用配额。

供应商已经成功后，只要媒体写入、角色绑定或后续交付失败，Worker 都会在当前任务租约下把本地可恢复结果写入 `tasks.result_json`：已完成对象保存资源引用，尚未完成对象暂存原内联正文；尚未提交的画布操作写入不公开的 `tasks.delivery_ops_json`。任务与会话列表只投影恢复标记，并且只读取不超过 1 MiB 的结果用于首图预览，较大的 Base64 检查点不会进入高频轮询响应；任务详情仍按用户显式请求读取完整检查点。正常路径在媒体全部就绪后先写同样的检查点，再提交任务成功、Agent 会话消息、结果表和画布操作的终态事务。任务进入“交付失败”后，用户点击“恢复已保存结果”会先续写 pending/未完成媒体，再重放会话与画布交付，全程不访问供应商或创建订单；人工恢复租约会在长 OSS 写入期间持续续期，并在每个对象之间重新核对，租约失效时不得继续写下一个对象。成功终态会清空 `delivery_ops_json`，避免把已提交操作再次恢复。

## 请求明细索引

`api_call_logs` 以 `created_at DESC, id DESC` 作为管理端分页和导出的稳定顺序。用户、渠道、任务、能力、模型和状态分别与 `created_at` 建立复合索引；任务恢复只从当前计费订单或当前任务尝试时间内读取供应商任务 ID，禁止跨重试轮次复用历史请求。

任务终态还会按 `task_id + billable + succeeded` 查询是否存在更早的供应商调用。这个判断不能依赖 `billing_order_id`：个人自定义渠道没有平台订单，但分镜首轮成功后，第二次结构修复即使在 DNS、参考资源或序列化阶段确认没有发出新请求，首轮仍可能由供应商计费，任务消息必须继续提示核账。平台系统渠道只有在不存在更早成功调用且当前请求可证明未建连时才能退款。

## 结构变更约束

- `channel_models.protocol` 由 GORM 自动建列，不单独维护手写 SQL 迁移。
- `channel_models.capability_config_json` 与 `capability_version` 由 GORM 自动建列；空的历史视频配置只按当前模型协议读取安全默认模板，不从客户端或旧 `models_json` 复活任意能力。
- 空协议表示继承渠道默认值，不代表自动猜测供应商；新建和从上游拉取的模型会显式保存当时的渠道默认协议。
- 修改模型协议属于强校验写路径，非法协议或与能力不匹配时必须拒绝保存。
- 渠道模型写入与 `model_channels.models_json` 投影必须同事务提交；服务启动会以未软删除的模型行为准修复漂移。存在任意模型历史时不得再从旧 JSON 执行初始化迁移。
- 渠道和模型管理入口必须先执行目录数量、标识长度与控制字符校验；上游目录分批插入，不能把供应商返回数量直接展开成一条无界 SQL。
- 系统文本模型测活结论与渠道 ID、Base URL、API Key、API 格式、模型协议和模型标识共同生成服务端 SHA-256 指纹；配置不匹配时公开接口不得返回旧结论，渠道或模型请求配置变更会清空状态。
- `shots.definition_json` 由 GORM 自动建列；结构化镜头只接受当前 `mingwant.short-drama.shot/v1`，不为旧字段增加隐式迁移分支。
- `idx_api_logs_task_created` 与 `idx_api_logs_capability_created` 由 GORM 自动建索引，用于任务恢复和按能力筛选的大数据量请求明细查询。
- `idx_tasks_status_next_poll` 由 GORM 自动建索引，用于后端重启后恢复到期的供应商轮询。
- `tasks.provider_call_state` 由 GORM 自动建列。新领取和显式重试的任务写入 `pending`，调用前审计事务将其改为 `preflight`，HTTP 建连前再以有效租约条件改为 `dispatched`。后续结构修复只续租和追加审计，不能把已经存在的 `dispatched` 降回 `preflight`；升级前空值与旧版 `prepared` 都不被当作“尚未调用”的证明。
- `tasks.request_key`、`tasks.probe_request_key`、`channel_probe_submissions` 与 `sessions.request_key` 由 GORM 自动迁移；`idx_channel_probe_submission` 随模型建立，`idx_tasks_user_active_request_key`、`idx_tasks_active_system_probe_key`、`idx_tasks_user_probe_request_key` 和 `idx_sessions_user_request_key` 在启动迁移中显式创建，以同时兼容 SQLite 与 PostgreSQL 的任务、系统测活、首次提交/接管提交重放及会话幂等约束。数据库账号必须具有建表、建列和建索引权限，迁移失败时服务应停止启动，不能在缺少去重约束时继续接单。
- `tasks.delivery_ops_json` 是结果交付检查点的私有部分，只在终态事务前暂存画布操作；任务列表和详情只公开是否可恢复，不返回操作正文。显式付费重试必须先拒绝仍有完整检查点的任务，恢复成功后才清空该字段。
- `tasks.provider_state_json` 是异步供应商的私有控制检查点。RunningHub 只保存与当前计费尝试和 taskId 绑定的结果节点、抢停与结果读取证据；成功终态和新的显式付费重试会清空该字段，失败或取消时保留以便只恢复原任务。
- `resources.source_task_id`、`source_attempt`、`source_path`、`content_sha256` 与 `quota_day` 由 GORM 自动建列；`idx_resources_task_output` 在启动迁移中显式创建。同一尝试的资源身份不能只依赖随机对象键，新的任务重试也不能沿用上一笔计费尝试的资源身份。
