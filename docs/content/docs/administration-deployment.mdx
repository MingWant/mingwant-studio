# 管理部署手册

本手册面向系统管理员和自部署维护者，覆盖管理员初始化、用户与积分、模型渠道、资源策略、存储、Linux 部署、HTTPS、备份恢复、版本更新、任务恢复和常见故障。

> 当前版本尚未完成构建、浏览器、Docker 和生产部署的全面验证。以下内容是与现有代码和脚本一致的操作手册，不代表已经通过真实生产环境验收。正式上线前必须在与生产相同的测试环境完成本文末尾的上线门禁。

## 一、先认识系统边界

| 组件 | 主要职责 | 持久化状态 |
| --- | --- | --- |
| Web | React 页面、画布、模型配置、任务和管理后台 | 浏览器 `localForage` 缓存、少量本地偏好和用户自定义 API 配置 |
| Backend | 登录、项目、资源、任务队列、模型中转、计费和审计 | SQLite 或 PostgreSQL、后端数据目录、`.settings-key`、上传资源 |
| Redis | 多实例并发、限流、熔断和任务协调 | AOF；不是项目和计费事实的唯一来源 |
| OSS | 可选的私有媒体对象存储 | 阿里云 OSS Bucket；对象生命周期由部署方管理 |
| Canvas Agent / Codex 插件 | 读取或操作画布、项目和生成工具 | 依赖当前 Web、后端和本地 Agent 会话 |

## 二、管理员初始化顺序

### 1. 创建第一个管理员

空数据库中的第一个注册账号自动成为管理员，不要求邮箱验证码。创建成功后立即确认：

- 能进入 `/admin`；
- 用户角色显示为管理员；
- 后端数据目录或数据库连接是预期目标；
- 没有因为错误数据目录创建第二套账号系统。

### 2. 配置登录与注册

进入“管理后台 → 登录与注册”：

- 默认关闭普通注册，只在确有需要时开放；
- 如果要求邮箱验证码，先在“邮件服务”配置并验证 SMTP；
- Linux.do 登录只能使用真实 HTTPS 授权、Token 和用户信息地址；
- 不要为了临时测试长期开放匿名注册；
- 变更后使用普通用户浏览器会话实际验证注册、登录和退出。

SMTP 主机只填写域名或 IP，不带 `smtp://`、端口、路径；有用户名和密码时必须选择 TLS 或 STARTTLS，系统拒绝通过明文 `none` 发送认证凭据。连接阶段最多等待 12 秒，连接建立后的问候、STARTTLS、认证、收件人、正文和退出共享 30 秒 deadline，避免异常邮件服务器永久占住注册请求。公共注册接口只返回“暂时不可用”等安全提示，详细 SMTP/数据库原因只进入 Backend 日志，不回传内部主机或 IP。

注册验证码有效期为 10 分钟。新码先以不可验证的 pending 记录落库并原子失效旧码，SMTP 完成后写入 `sent_at` 才能使用；邮件发送失败、进程中断或激活落库失败时，即使清理记录再次失败，pending 码也不能注册。单个验证码最多允许 5 次错误，次数保存在数据库并在最终创建用户的事务中再次校验，换 IP 或 Backend 实例不能绕过。发送入口同时受管理员配置的 IP 小时频控和每个收件人每分钟一次的摘要键频控；已注册邮箱返回与正常请求相同的成功结构，不直接暴露账号是否存在。

### 3. 配置系统渠道和模型

进入“管理后台 → 系统渠道”：

1. 新增渠道，填写名称、默认协议、Base URL、API Key 和并发策略。
2. 进入“模型管理”，拉取或手工新增模型。
3. 为每个模型设置能力、真实请求协议、计费方式、积分价格和启用状态。
4. 对文本模型点击“测活”，确认后台信息抽取、随机码校验、耗时与 API 日志均正常。
5. 再用管理员测试账号执行一笔完整业务任务，验证计费和结果回填后向普通用户开放。

文本测活通过后会自动追加一次“测试工具调用”；也可以手动重做：后台用可恢复任务沿用同一渠道、协议和端点发送固定的 `probe_extract_record` 无副作用函数，校验工具名、参数和随机码，输出上限为 512 token，不执行画布写操作；文本测活和工具诊断共用活动互斥与提交幂等，响应丢失不会重发供应商请求。普通用户不能发起系统渠道测活，只能使用管理员发布的能力状态。

“拉取模型”只导入缺失项，新模型仍应由管理员定价并手工确认启用。一个渠道可以包含多种能力，每个模型的协议可以覆盖渠道默认协议。

模型表是启停、协议和定价的权威来源，渠道记录里的旧模型数组只是兼容投影。保存渠道、启停或删除模型时两者会在同一事务中更新；Backend 启动时也会自动修复历史分步写入造成的漂移，但不会从旧数组复活已经停用或软删除的模型。若管理员在一次较慢的“拉取模型”期间修改了 Base URL、API Key 或协议，该次旧目录会以 409 放弃写入，应按新配置重新拉取；这样不会把旧供应商的模型误挂到新渠道。

管理员账号与登录态、公告、系统渠道与模型、成本和售价、邮件/Linux.do/开放注册/OSS、分镜模板、积分与运行策略、人工调账、兑换码及待核对订单的业务变更，都会和管理员审计事件在同一数据库事务中提交。若审计表不可写，接口会失败且账号、会话、余额、流水、订单或配置整体回滚，不会出现“页面报错但操作已经生效”；正常成功则只产生对应的审计事件。并发减少管理员权限时会先按固定顺序锁定当前可用管理员，不能让两个请求各自基于过期数量同时移除最后管理员。只有“人工查询供应商任务”这类不可回滚外部动作会先记录查询意图，再访问供应商。

审计只保留定位操作所需的状态、数量、模型、价格、处置理由以及“凭据是否变化”等业务字段；不会保存 API Key、OSS 访问密钥、SMTP 密码、OAuth Client Secret、Base URL、供应商响应正文或完整分镜提示词。审计落库失败时不要立即重复提交涉及资金的操作，应先检查数据库迁移和 `admin_audit_events` 写权限，确认原事务确实已回滚。

邮件、Linux.do、OSS 等页面用空白密钥表示“保留当前凭据”。保存时 Backend 会在事务内复核页面最初读取的设置版本；若另一位管理员已经修改、创建或重置同一设置，本次返回 409 且不会覆盖对方的新密钥。看到冲突提示时刷新页面、重新核对非密钥字段后再保存，不要连续点击提交。

模型目录不是无限输入：上游响应最多读取 8 MiB，`data` / `models` 原始条目各不得超过 5000，去重后单渠道最多保存 2000 个模型，模型标识和显示名分别限制为 120、160 个字符且不接受控制字符。新发现模型以 100 条一批写入，避免 SQLite 或 PostgreSQL 参数上限被异常目录击穿。浏览器提交的目录凭据、渠道和单模型管理请求也有独立正文上限；超过边界应修正供应商目录或拆分渠道，不要直接扩大数据库字段。

测活会发起一次真实但极小的供应商请求，不扣平台积分。任务持久化到后台，页面关闭后仍会继续；Chat Completions、Responses 与 Gemini GenerateContent 都优先使用 SSE 流式接收，并分别用 `max_completion_tokens: 256`、`max_output_tokens: 256` 与 `generationConfig.maxOutputTokens: 256` 限制探针输出。Gemini 原生文本使用 `x-goog-api-key` 和 `streamGenerateContent?alt=sse`；系统渠道填写官方根地址时服务端会补 `/v1beta`，已填写 `/v1` 或 `/v1beta` 则原样使用。Kimi K3 默认推理强度很高，探针和要求流式的长分镜会显式使用 `reasoning_effort: low`；其他模型不注入这一供应商选项。OpenAI 兼容探针和普通短文本只有在供应商以 400/422 明确拒绝 `stream` 参数时才允许回退一次非流式；Gemini 原生流式端点失败时不会再补发另一笔 `generateContent`。分镜等长结构化任务也不会补发非流式请求，Gemini 分镜会请求 `application/json` 响应 MIME 并排除 thought 片段。结果显示“渐进流式接收”时，管理员可判断它更适合慢推理；后端会同时记录供应商首字节、正文读取批次、首尾数据到达间隔、后续分片累计等待和最长单次等待。合法 SSE 若所有正文几乎同时到达，会标记“SSE 完整，但未观察到渐进分片”：它可能只是短响应被网络合并，也可能是网关缓冲到最后才返回，因此不能证明长请求稳定，但不阻止普通用户在费用确认后尝试长分镜。完整 JSON 或非流式回退同样显示风险警告。流式只能降低连接空闲导致的超时，不能保证绕过供应商自身的 524。

探针创建同时使用永久提交幂等与活动配置互斥。Web 在请求前用极小的本地记录保存随机提交键，`idx_tasks_user_probe_request_key` 让首次创建者重发该键时永久返回原任务；接管其他活动探针的提交键则写入 `channel_probe_submissions`，同样永久指向实际接管的任务。即使接管响应丢失后任务已进入终态，也不会再调用供应商。相同自定义配置只在当前用户内复用；同一系统渠道与模型再由 `idx_tasks_active_system_probe_key` 在全部管理员之间全局互斥。双击、多标签页或多 Backend 实例并发提交时，后端返回原活动任务，接管者可以继续轮询，但不会创建第二次供应商调用；收到明确创建响应后的下一次操作才使用新提交键。系统任务的全局接管只向管理员公开固定探针状态，不会因此开放其他用户的自定义渠道任务或密钥。

系统渠道的文本模型会把最近一次流式能力状态、真实传输方式、耗时和时间写入模型目录；模型管理列表直接显示“流式通过 / SSE 疑似缓冲 / 非流式风险 / 未通过 / 需重测”。状态通常由测活写入；真实调用若只观察到完整但没有时间跨度的 SSE、完整 JSON 非流式响应、524、连接中断或明确拒绝流式，也会自动把模型降级，避免下一位用户重复踩坑。状态与渠道 Base URL、密钥、协议和模型标识绑定，任一请求配置变化都会失效，超过 7 天也按过期处理。个人自定义渠道在当前用户浏览器只保存不含密钥、提示词或响应正文的小型结论及测活任务 ID。在线短 Agent 对已知风险模型默认只授权 1 次调用；影视项目、脚本分镜和任务中心 Agent 分镜会把未测活、疑似缓冲或过期状态作为风险提示，但不会因为探针失败直接阻止普通用户调用。手动交付模式仍是一个更短的受限路径：无论测活是否通过，短剧入口都只通过一次有界短文本请求写入 3–5 镜头 script 节点，不依赖 Function Calling，不创建后台长分镜或视频任务；文本请求截断或完全无法识别镜头时停止。系统渠道在计费预留前读取模型状态只用于确认文案和预算提示；自定义渠道的测活任务 ID仍可保存供管理员审计，但不再作为普通用户调用授权。

SSE 完整性和渐进传输规则带版本号。升级到当前诊断规则后，旧版探针和旧配置指纹不会继续显示为当前配置的绿色诊断，管理员需要重新测活才能获得准确状态；但这不会禁止普通用户在费用确认后尝试调用。这样既能排除缺少结束标记的半截流和“最终一次性返回合法 SSE 文本”的缓冲响应，也不会把管理员诊断误当成用户授权。

在线画布 Agent 每条消息由用户选择 `1 / 2 / 4` 次文本推理预算，默认 2 次、硬上限 4 次；网页不再向在线 Agent 工具编排请求注入固定的 2048/4096 token 输出上限，模型按自身上下文和供应商策略决定长度。Kimi 工具编排仍使用 low 推理强度。Kimi Chat 工具调用返回的 `reasoning_content` 会作为协议状态在内存中原样带入工具后的下一轮，但不会显示给用户、写入会话消息或在线诊断日志。Kimi 兼容 Chat 还会按用户意图收窄首轮工具 Schema：只读请求使用 `kimi-read`，短剧/分镜入口只发送影视入口工具并使用最小画布上下文，普通写画布使用 `kimi-write`，生成任务使用 `kimi-generation`，未识别意图才回退 `kimi-compact`；完整画布快照仍由后台影视任务接收，后续轮次沿用首轮档位，降低兼容网关因无关深层 Schema 或大上下文拒绝请求的概率。系统渠道会为每一轮代理请求分别建立请求和积分记录，自定义 API Key 则可能由供应商逐次收费；这个数字不包含 Agent 工具另行创建的图片、视频、音频和影视分镜任务。会话会持久记录已使用次数，工具待确认、达到上限或遇到上游 408、499、除 501 外的 5xx 与连接不确定错误时不会自动开始下一轮。尚未完成或失败的工具诊断只用于风险提示并默认限制为 1 次，用户仍可发起本轮真实调用；只有真实请求没有返回完整工具调用、上游错误或明确截断时才停止后续轮次。上游完整结束但没有可用文本或完整工具调用、首轮忽略 `tool_choice=required`，或以 Chat `length`、Responses `response.incomplete`、Gemini `MAX_TOKENS` 明确截断时，也按已发生的一次调用停止；明确截断会由代理完整交付并正常结算当前调用，但半截正文和工具参数不得进入画布或下一轮。

在线 Agent 调用 `canvas_create_cinematic_session` 时，普通消息预算确认不等于影视结构修复授权。工具执行前会再显示一次“允许最多一轮结构修复”的费用确认；用户取消时不会创建影视后台会话，也不会访问供应商。确认结果会和浏览器创建键一起保存，响应丢失或刷新恢复时只沿用原授权；旧本地记录没有该字段时按未授权处理，首轮结构异常只失败并明确“没有发起第二次请求”。

在线 Agent 的红色“停止”会向当前浏览器请求发送取消信号；系统渠道会把浏览器断开记为计费待核对，但供应商未必停止计算或收费。停止后必须终止本轮工具循环，不得自动重试。模型请求、工具执行或工具确认未结束时，前端会阻止收起面板和站内离开，并在刷新/关闭页面时触发浏览器离开警告；这样可避免组件卸载后仍发起下一轮模型请求，或留下无法恢复的工具确认上下文。后台影视 Agent 会话有持久任务 ID，不适用“网页连接即任务生命周期”的判断。

本地 Canvas Agent 使用 SSE 接收工具调用，并通过本机 HTTP 接口同步画布状态和回传工具结果。自动打开画布时，地址和 Token 放在 `#agentUrl=...&agentToken=...` fragment，不能放进 `?query`；fragment 不会发送给 Web 服务器，网页读取后立即清除，Token 只保存到当前标签会话的 `sessionStorage`。网页只允许连接 `127.0.0.1`、`localhost` 或 `::1`，普通请求和 SSE 都通过 `X-Canvas-Agent-Token` 请求头鉴权，本地服务不接受 `?token=`。连接成功必须以初始快照写入成功为准，而不是只看到 SSE `hello`；状态写入按顺序执行且单次最多等待 15 秒，每轮 Codex 发送前再次强制同步。画布写工具必须先同步修改后的快照，再确认工具完成，自动连接也不会关闭确认。任何状态写入或结果回传出现非 2xx、异常响应或超时，Web 会断开本地 Agent，防止后续工具继续读取旧状态。排障时不得把 Token、完整画布敏感内容或附件 Base64 粘贴到公共日志。

### 4. 配置积分

系统渠道通过积分计费。上线前检查：

- 模型按次或按秒计费是否与供应商账单口径一致；
- 普通用户是否有足够余额；
- 失败、退款、待核对和人工恢复是否能形成正确账本；
- “积分运营”中的人工调账有操作理由和审计记录；
- 兑换码批次的用途、数量和发放范围明确。

不要在没有价格和退款验证的情况下开放付费模型。

### 5. 配置资源与请求策略

进入“管理后台 → 资源与策略”。配置会即时生效，主要分为：

- 资源和账号配额：单文件、每日上传、账号文件总量、结构化数据、任务历史、素材、画布和会话数量；
- 任务与并发：Worker 并发、全局渠道并发、单账号活动任务上限；
- 任务超时：文本、图片、音频、视频、分镜和默认任务时限；
- 业务频控：注册、登录、验证码、上传、任务创建和渠道中转；
- 渠道保护：请求体、响应体、并发、超时、熔断失败次数和熔断时长。

先按供应商限额和服务器资源使用保守值。只增加 Worker 并发而不增加数据库、Redis、渠道和供应商能力，通常只会把故障放大。

登录有两个独立的 10 分钟窗口：IP 频控限制同一来源批量撞库，账号频控跨 IP 聚合同一用户名或邮箱，换代理不能重置账号计数；账号原文不会写入 Redis 键。PostgreSQL 部署由 Redis 统一所有实例的窗口、渠道槽位和熔断状态；SQLite 单实例使用进程内协调器，并每分钟回收已经过期的限流键、槽位 Token 和空 scope，避免长期运行后内存只增不减。触发限制时响应的 `Retry-After` 使用对应真实窗口秒数，而不是统一写成 60 秒。

新安装的默认文本任务时限为 15 分钟，分镜任务总时限为 30 分钟，系统与自定义同步模型中转默认等待 35 分钟。文本测活也使用文本时限；分镜时限要同时覆盖首轮和一次已授权修复。已经保存过“资源与策略”的部署不会被代码默认值静默覆盖，请按实际模型耗时手工调整任务时限和“同步模型中转超时”。同步中转从请求进入 Backend 起计算总时限，自定义渠道的请求体读取、系统渠道的并发槽位等待及上游响应都包含在内；供应商调用前到期不会产生上游费用，系统渠道若已预留积分会退回。请求已经发出后到期则按费用待核对处理。普通任务和影视 Agent 会话均每 5 秒跟踪后台终态，不再用固定 4、12 或 13 分钟抢先判失败；状态查询遇到断网、429 或 5xx 会退避到最多 30 秒并在服务恢复后继续。超时从任务首次开始计算，Worker 每 15 秒续租；把本地时限调大只能允许后台继续等待，不能消除供应商或 CDN 主动返回的 524。

任务与同步中转时限不能超过当前 Backend 停机排空窗口；管理后台保存时会强校验，“自用模式”预设也会把这些时限收敛到当前安全窗口，而不是填入部署无法兑现的超长等待。需要更长任务时，先修改 `.env` 中两项停机变量并重启，确认 Backend 正常启动后再保存业务策略。

后台任务的图片、音频、视频或未知类型一旦在可能发出请求后超时，订单必须保持“待核对”，错误必须明确禁止立即重试；视频若已经记录供应商任务 ID，应先走任务详情的“手动查询任务”。只有渠道并发槽位等待超时等正文同时证明“没有调用供应商”的情况才按未调用退款，并允许在现有任务释放后重新提交。任务终态已保存但退款、待核对或结算更新失败时，任务日志必须出现独立错误，订单保持非终态以继续阻止重复生成。

例如供应商后台显示一笔 `非流式` 调用用了约 4 分 46 秒并生成近 6000 token，而本系统先收到 524，说明中间网关已经在完整响应返回前断开；此时 15、30 或 35 分钟本地配置都不是根因。新版会把测活限制在 256 token，在线 Agent 不再由网页注入固定的 2048/4096 token 输出上限，但仍会拒绝供应商明确标记的截断结果；后台影视分镜首轮和一次授权修复仍各有 4096 token 上限并优先生成 3–5 镜，降低短控制请求和常见短剧分镜触发 524 的概率。更长内容应拆成多次任务。长内容建议改用持续发送 SSE 分片的渠道，测活显示“渐进流式接收”可作为管理员选型依据，也可使用供应商明确提供的异步任务接口。不要把同一请求立即改成更长 timeout 后重放。

Backend 在任何供应商建连前都会解析并复核目标主机，DNS 预检继承请求取消信号且最多等待 5 秒。任务配置解析、参考 OSS 读取和 NewAPI 参考素材 URL 校验同样继承任务截止时间；在这些阶段取消不会继续占住 Worker 或误报为已经调用模型。若这里失败，任务会明确说明本次供应商请求没有发出；系统还会查询同一任务更早的成功请求：首轮尚未调用时退回平台预留积分，首轮已经成功而第二次结构修复预检失败时仍提示核对原费用。没有平台订单的个人自定义渠道也会用请求明细识别更早调用，但只提示到供应商后台核账，不会声称平台退款。若频繁出现“地址预检失败”，应在 Backend 所在容器内检查 DNS、域名拼写和私网上游白名单，不要把它与已经收到上游 524 的费用不确定错误混为一谈。

升级后端会自动增加 `tasks.request_key`、`sessions.request_key`、生成资源来源字段、活动任务部分唯一索引、会话创建唯一索引和任务生成资源唯一索引。PostgreSQL 部署账号必须拥有表结构与建索引权限；SQLite 数据文件必须可写。迁移失败时应修复权限并重新启动，不能跳过索引后继续开放任务创建。

### 6. 配置存储

未启用 OSS 时，媒体写入后端数据目录。启用平台 OSS 后，新上传和新生成资源写入私有 OSS；资源仍通过登录鉴权接口访问，不应公开 Bucket。

进入“管理后台 → 存储服务”，配置：

- Provider：当前支持阿里云 OSS；
- Region；
- Endpoint；
- Bucket；
- 路径前缀；
- AccessKey ID 和 AccessKey Secret。

普通用户也可以在“配置与用户偏好 → 我的 OSS”保存个人 OSS。个人配置启用时优先于平台存储；历史资源固定使用创建时的配置版本。

必须保留后端数据目录中的 `.settings-key`。OSS Secret 和异步任务中的 API Key 依赖它解密；只恢复数据库而遗失该文件，会导致历史密文无法使用。

删除节点或素材不会自动删除 OSS 远端对象。应另行制定 Bucket 生命周期、孤儿对象审计和客户数据删除流程。

## 三、部署前安全基线

正式接入真实素材前，至少满足：

- 使用自有域名和有效 HTTPS 证书；
- 主页面只通过可信反向代理访问；
- 数据库、Redis和后端内部端口不暴露公网；
- `CANVAS_CORS_ORIGINS` 只填写精确的 `http(s)://主机[:端口]`；`*`、路径、查询参数和账号信息都会让 Backend 拒绝启动，同源部署通常无需配置；
- `CANVAS_ALLOW_PRIVATE_UPSTREAMS=false`，除非明确审计了内网模型服务；
- 若允许私有上游，只在 `CANVAS_ALLOWED_PRIVATE_UPSTREAM_HOSTS` 中列出必要主机；
- 普通注册默认关闭，管理员账号使用独立强密码；
- `.env`、数据库备份和后端数据目录仅管理员可读；
- API Key、Cookie、Authorization 和 `.settings-key` 不进入 Git、日志或工单截图；
- 已制定备份、恢复、密钥轮换、客户隔离和数据删除方案。

用户自定义 API Key 默认只保存在按账号隔离的当前标签页会话；退出、切换账号或关闭标签页后清除。用户只有在可信个人设备上明确开启“在此设备记住”，密钥才会进入独立的账号级浏览器持久区，普通配置快照、画布、导出包和云同步不携带明文。旧版本已经长期保存的密钥会无损迁移到持久密钥区并显示为已开启，用户可以关闭开关把它移回当前会话。浏览器持久区无法抵御恶意扩展、同源 XSS 或本机用户目录泄露；异步任务还可能把所选密钥加密后提交到 Backend。因此即使没有平台系统渠道，也必须把 Web、Backend 和浏览器运行环境都视为能够接触用户密钥的可信系统。

媒体模型的浏览器边界是强制的：图片、视频和音频创建及轮询只能先进入 Backend 持久化任务，不能从 Web 直接请求供应商，也不能借系统渠道或 `/api/ai/custom` 同步代理绕过任务幂等、计费和恢复。浏览器保留的在线 Agent 文本与模型目录请求通过受限同源中继；因此部署只需正确配置浏览器到自有 Web/Backend 的 HTTPS 与 CORS，Backend 到供应商属于服务端出站连接。

## 四、部署方式 A：本地 Docker

适合测试整套 Web 和后端：

Windows PowerShell 推荐先用仓库自带的预检脚本：

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\start-local.ps1
```

脚本会在构建前检查 Docker Linux Engine、Compose 能力和实际 Web 端口。默认读取当前进程环境变量，其次读取仓库根目录 `.env` 中的 `CANVAS_HTTP_PORT`，最后使用 `3000`；如果端口被本项目以外的程序占用，会显示进程并在创建或修改容器前退出。需要改为 3001 时：

```powershell
$env:CANVAS_HTTP_PORT = "3001"
powershell -ExecutionPolicy Bypass -File .\scripts\start-local.ps1
```

脚本允许原有 MingWant Web 容器继续占用同一端口，以便原地更新；启动后会按实际端口重试 `/api/health`，失败时输出容器状态和最近日志。它不会自动启动 Docker Desktop，也不会删除数据卷。

Compose 实际卷名还包含项目标识。脚本会解析并打印该标识，首次健康启动后写入 `.local/compose-project-name`；仓库目录改名或 `COMPOSE_PROJECT_NAME` 改变时，后续启动会在 `compose up` 前停止，避免误挂载新卷。遇到提示应恢复原目录名或原环境变量，不要直接删除标识文件。全新、长期手工运行的安装可在第一次启动前于 `.env` 固定 `COMPOSE_PROJECT_NAME=mingwant-studio`；已有数据的实例必须沿用原值。

macOS、Linux 或需要手工执行时使用：

```bash
docker compose -f docker-compose.local.yml up -d --build --wait
docker compose -f docker-compose.local.yml ps
```

默认访问 `http://localhost:3000`；设置 `CANVAS_HTTP_PORT` 后访问对应端口，并确认同一地址下 `/api/health` 的三项组件检查均为 `ok`。

本地 Docker 只向宿主机发布 Web 端口，Backend 的 8080 留在 Compose 网络内。不要把宿主机访问 `127.0.0.1:8080` 失败误判为后端故障；以 Web 地址下的 `/api/health` 为准。

本地 Compose 使用 SQLite 和命名卷：

- `backend-data`：数据库、`.settings-key`、上传和后端资源。

停止服务使用 `stop`，不要使用 `down -v` 删除卷。

## 五、部署方式 B：Linux 服务器源码部署

源码脚本会：

1. 检查 Linux 和 root 权限；
2. 安装基础工具和 Docker；
3. 从明确指定的自有仓库克隆或快进更新；
4. 生成 PostgreSQL 随机密码和 `.env`；
5. 构建 Web 和 Backend 镜像；
6. 启动 PostgreSQL、Redis、后端和 Web。

安装器在下载或更新源码前会先确认 Docker Engine 已启动、处于 Linux 容器模式，且 Compose 支持 `--wait` 和 `--wait-timeout`；这一步失败时不会继续拉取源码、部署文件或镜像，也不会启动 Compose。若看到 Engine 未就绪提示，请先启动 Docker 服务；若提示 Compose 能力不足，请更新 Docker Compose 后再执行安装器。

当前项目没有可安全默认使用的公开派生仓库地址，必须显式提供 `REPOSITORY_URL`。建议先下载并审阅脚本：

```bash
curl -fsSL https://raw.githubusercontent.com/你的账号/mingwant-studio/main/scripts/install-server.sh -o /tmp/mingwant-install.sh
less /tmp/mingwant-install.sh
sudo REPOSITORY_URL=https://github.com/你的账号/mingwant-studio.git bash /tmp/mingwant-install.sh
```

可选参数：

```bash
sudo \
  REPOSITORY_URL=https://github.com/你的账号/mingwant-studio.git \
  REPOSITORY_REF=main \
  INSTALL_DIR=/opt/mingwant-studio \
  COMPOSE_PROJECT_NAME=mingwant-studio \
  CANVAS_HTTP_PORT=3000 \
  bash /tmp/mingwant-install.sh
```

如果安装目录已经是 Git 仓库，脚本只接受没有未提交代码改动的工作区，并使用 `git pull --ff-only` 更新。它不会覆盖一个已有且非本脚本管理的非空目录。全新安装生成的 `.env` 会固定 `COMPOSE_PROJECT_NAME`；同一台服务器部署多套实例时，每套必须在首次安装前使用不同且长期不变的项目标识。已有 `.env` 不会被脚本擅自补写或改名；升级时若临时传入的项目名和既有值不一致会在启动容器前停止。旧 `.env` 如果没有固定值，安装器现在也会在启动前停止，要求先人工运行 `docker compose config` 核对实际项目名和数据卷，再把确认后的合法值写入 `.env`；不能让 Compose 静默按目录名选择卷。

服务器 Compose 默认把 Web 端口绑定到 `127.0.0.1`，安装完成后输出的是本机 Web 上游地址，不是公网访问地址。请在同一台服务器的 HTTPS 反向代理中转发到该地址；如果确实需要让其他主机直接访问，应由运维明确修改 Compose 绑定并同时承担 HTTPS、Cookie 和 `X-Forwarded-Proto` 的安全边界。

## 六、部署方式 C：已发布镜像

镜像安装需要同时指定同一发布版本的部署配置、安全备份脚本和两个派生镜像，防止拉到不包含本项目改动的上游镜像，或部署出没有可执行恢复入口的服务器：

```bash
curl -fsSL https://raw.githubusercontent.com/你的账号/mingwant-studio/v0.1.0/scripts/install-server-image.sh -o /tmp/mingwant-image-install.sh
less /tmp/mingwant-image-install.sh
sudo \
  COMPOSE_URL=https://raw.githubusercontent.com/你的账号/mingwant-studio/v0.1.0/docker-compose.deploy.yml \
  BACKUP_SCRIPT_URL=https://raw.githubusercontent.com/你的账号/mingwant-studio/v0.1.0/scripts/backup-server.sh \
  MINGWANT_BACKEND_IMAGE=ghcr.io/你的组织/mingwant-studio-backend:v0.1.0 \
  MINGWANT_WEB_IMAGE=ghcr.io/你的组织/mingwant-studio-web:v0.1.0 \
  bash /tmp/mingwant-image-install.sh
```

安装器会把备份脚本保存为 `/opt/mingwant-studio/scripts/backup-server.sh`，并在部署结果中打印安全备份命令。全新安装同样会在 `.env` 固定 `COMPOSE_PROJECT_NAME`；已有 `.env` 如果缺少该值或包含非法值，安装器会在拉取镜像和启动 Compose 前停止，要求先人工核对原项目名和数据卷。一台主机的多套实例必须在首次执行时分别传入不同值。`COMPOSE_URL`、`BACKUP_SCRIPT_URL` 和两个镜像标签必须对应同一次发布；不要让 `main` 分支脚本管理固定旧镜像。

私有 GHCR 包可以额外提供 `GHCR_USERNAME` 和 `GHCR_TOKEN`。Token 只应通过受控环境传给安装脚本，不应写进仓库或命令历史；部署完成后检查 Docker 凭据存储。

镜像安装器同样会在登录 GHCR、下载部署配置和拉取镜像前完成 Docker Engine 与 Compose 预检；预检失败不会替换已有部署文件。

生产环境优先固定版本标签或镜像摘要，不要依赖随时变化的 `latest`。

## 七、部署环境变量

| 变量 | 用途 | 生产建议 |
| --- | --- | --- |
| `POSTGRES_DB` | PostgreSQL 数据库名 | 使用独立数据库 |
| `POSTGRES_USER` | PostgreSQL 用户 | 使用最小权限专用用户 |
| `POSTGRES_PASSWORD` | PostgreSQL 密码 | 随机生成并受控备份 |

| `CANVAS_CONTAINER_STOP_GRACE_PERIOD` | Docker 在强制结束 Web/Backend 前保留的时长 | 默认 `45m`；必须至少比应用排空时长多 1 分钟 |

安装脚本会在 `/opt/mingwant-studio/.env` 或自定义安装目录生成配置。应限制权限并纳入加密备份。

## 八、HTTPS 和反向代理

外部反向代理只需要指向 Web 服务，Web 内部会把 `/api` 转发给后端。以下是结构示例，证书配置应交给实际使用的 Nginx、Caddy 或云负载均衡：

```nginx
server {
    listen 443 ssl;
    server_name studio.example.com;

    location / {
        proxy_set_header Host $http_host;
        proxy_set_header X-Forwarded-Host $host;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_http_version 1.1;
        proxy_buffering off;
        proxy_read_timeout 3600s;
        proxy_send_timeout 3600s;
        send_timeout 3600s;
        proxy_pass http://127.0.0.1:3000;
    }
}
```

内置 Web 代理和 Backend 会对系统渠道 SSE 设置 `X-Accel-Buffering: no` 并逐块刷新；外层反向代理仍必须允许长连接且不能重新缓冲。如果上游直到最终结果才发送任何响应，或供应商自己的 CDN 主动返回 524，本系统无法用更长的本地超时绕过它。此时应改用真正支持流式的接口/渠道，或联系供应商提高其网关时限。

Backend 自身只对请求头设置 15 秒上限，并把空闲 Keep-Alive 设为 2 分钟；后者不限制正在执行的请求。服务端刻意不设置全局 `ReadTimeout` / `WriteTimeout`，否则大文件上传或有效 SSE 会被统一时钟提前切断。安全边界由各业务请求体上限、同步中转总时限、后台任务时限和用户取消共同承担。

Backend 收到 `SIGTERM` 或 `SIGINT` 后会立即停止 Worker 领取新任务并把健康状态切为 503，同时停止接受新 HTTP 连接；已经进入处理中的在线 Agent/SSE 和后台任务会在同一个排空窗口内继续，完成后进程才退出。内置 Web/Nginx 使用 `SIGQUIT`，让正在代理的 SSE 先自然结束。Compose 默认给应用 40 分钟排空、给两个容器 45 分钟强制结束宽限，覆盖默认 35 分钟同步中转与 30 分钟分镜任务。如果排空到期，Backend 会关闭剩余连接并额外等待最多 30 秒，让请求日志、任务终态和费用待核对写入完成。管理员若调大任何任务或同步中转时限，必须先同时把这两个环境变量调大，并让容器宽限至少多 1 分钟；Compose 会把两个值同时交给 Backend，格式、余量或已有运行策略不满足约束时会在启动阶段明确失败，管理后台也会拒绝保存超过当前排空窗口的时限。`docker kill`、`kill -9`、宿主机断电和超过宽限的任务无法被优雅保护，重启后仍按供应商调用检查点进入退款、原任务查询或费用待核对，绝不能自动重放。

内置 Web 会统一发送 CSP、`X-Content-Type-Options: nosniff`、`X-Frame-Options: SAMEORIGIN`、`Referrer-Policy: no-referrer`、浏览器能力禁用策略和旧插件策略。主题初始化已经改为同源静态脚本，因此 CSP 不需要开放内联 JavaScript；仅为 Ant Design 动态样式保留 `style-src 'unsafe-inline'`，为人脸检测与本地合片保留 Blob Worker 和 `wasm-unsafe-eval`，没有开放风险更高的通用 `unsafe-eval`。用户 OSS、签名媒体、本地回环 Canvas Agent 与 SSE 仍在兼容范围内。Backend 即使绕过 Web 被直接访问，也会给纯 API 响应发送更严格的 `default-src 'none'`、`frame-ancestors 'none'` 和 `sandbox`。

HSTS 只有在内置 Web 看到可信的 `X-Forwarded-Proto: https` 时才发送，默认值为一年且不自动包含子域。外层代理必须像上例一样覆盖该头，不能把客户端自己提交的值原样透传。确认整个主域及所有子域都永久支持 HTTPS 后，才由运维在最外层统一决定是否增加 `includeSubDomains` 或申请 preload；错误开启会让仍使用 HTTP 的站点长期无法访问。

Backend 会在连接数据库前校验 CORS 配置：不接受 `*`、带路径/查询/用户信息的 URL，也不会把任意 localhost 端口或客户端提交的 `X-Forwarded-Host` 当成可信来源。同源请求必须同时匹配公开协议与原始 `Host`；本地 Vite 等跨端口开发环境也要显式列入 `CANVAS_CORS_ORIGINS`。浏览器发来的写请求若没有 `Origin`，但 `Sec-Fetch-Site` 明确表示 `cross-site`，会在进入业务处理前返回 403。外层与内置代理因此必须像上例用 `$http_host` 保留原始 Host 及非标准端口、覆盖 `X-Forwarded-Proto`，不要信任客户端自带的转发头。

登录 Cookie 使用 `HttpOnly`、`SameSite=Lax`，在 HTTPS 或可信代理声明 HTTPS 时增加 `Secure`；数据库只保存随机 Token 的 SHA-256 哈希。每次创建会话都会在同一事务中清理过期记录，并只保留该账号最近 20 个活动会话，超过上限的最旧会话自动失效。用户可在侧栏账号菜单点击“退出其他会话”，只保留当前浏览器。退出登录会先请求撤销当前服务端会话，并无论撤销是否成功都立即让浏览器 Cookie 过期；若数据库删除失败，接口返回明确的 500 提示，管理员必须检查并撤销可能残留的服务端会话，不能把本机已退出误认为令牌已经失效。

管理员修改用户密码、角色或启停状态时会撤销该用户的全部现有会话；数据库删除失败会让本次安全变更明确失败，不再忽略错误后留下旧会话。改显示名称或邮箱不会强制退出。角色调整后应通知用户重新登录，不要把已有页面尚未刷新视为权限仍有效。

Backend 不只依赖上游 `Content-Type`：请求已明确携带 `stream=true`、`Accept: text/event-stream` 或 Gemini `alt=sse` 时，会读取最多 64 字节的协议前缀识别被误标为 JSON 的真实 SSE，随后立即恢复逐块透传。反过来，只有事件是合法 JSON 且出现 `[DONE]`、`response.completed`、`finish_reason`、Gemini `finishReason` 等完成标记，才会结算为成功。流读取中断、损坏事件、干净 EOF 但缺少完成标记或响应超限都会在原 SSE 中追加 `stream_incomplete` 错误，阻止在线 Agent 使用半截结果；系统渠道订单进入待核对，自定义 API Key 提示先到供应商核账。

后台 Worker 的测活、脚本分镜和影视 Agent 不经过浏览器流式代理，但采用相同完整性与渐进传输标准：完整 JSON 即使被误标为 SSE 也会按非流式风险记录；SSE 必须包含可解析事件、明确结束标记，并且首包之后的上游正文读取累计实际等待达到 50ms，才能记为“适合慢任务”的诊断。这样连续快速的小分片也能累计成为证据。该判定测量的是上游 `Read` 本身，不把本地解析、浏览器写入背压或读取之间的调度间隔算成供应商分片。低于该可观测阈值的完整 SSE 不会判定任务内容失败，而是标记为“渐进分片未证实”并在费用确认中提示风险；普通用户仍可明确确认后发起长分镜。连接只返回半截分镜 JSON 后正常关闭时，任务会直接失败并进入费用核对边界，不会把半截正文交给分镜解析器，也不会借“结构修复”再自动产生第二笔请求。

系统渠道的真实在线 Agent 调用也会更新模型流式诊断：完整且观察到跨时间分片的 SSE 记为“流式通过”，完整但几乎同时到达的 SSE 记为“SSE 疑似缓冲”，完整 JSON 记为“非流式风险”，524、流损坏或缺少结束标记记为“未通过”。观察结果绑定请求开始时的渠道、密钥、协议和模型指纹；管理员修改配置或完成更新的测活后，迟到旧请求不能覆盖新结论。诊断更新用于管理员查看和后续费用提示，不会自动禁止普通用户的新请求。

部署后：

- 防火墙阻止公网直接访问 3000、8080、PostgreSQL 和 Redis；
- 浏览器只使用 `https://studio.example.com`；
- 用浏览器网络面板或 `curl -I` 确认主页面具有 CSP、`nosniff`、`SAMEORIGIN`、权限策略与 HSTS，HTTP 本地环境不得误发 HSTS；
- 同源请求必须同时匹配协议与 Host；确需跨域时才设置精确的 `CANVAS_CORS_ORIGINS=https://可信来源`，不同 localhost 端口也不例外；
- 验证登录 Cookie、注册、退出及服务端会话撤销、上传、大文件、流式生成和画布分享链接；
- 检查反向代理上传大小和超时，不要让它小于后台资源策略。

## 九、日常状态检查

服务器部署默认在安装目录执行：

```bash
cd /opt/mingwant-studio
docker compose --env-file .env -f docker-compose.deploy.yml ps
curl -fsS http://127.0.0.1:3000/api/health
docker compose --env-file .env -f docker-compose.deploy.yml logs --tail=200 backend
```

`/api/health` 不再只表示 HTTP 进程存活：它会分别检查 `database`、`coordination` 和 `worker`。三项全部为 `ok` 时返回 HTTP 200；数据库不可达、Redis/协调器失效、Worker 无法领取任务或调度心跳超过 10 秒时返回 HTTP 503。响应只给组件级原因，不回传数据库 DSN、Redis 地址或底层连接文本。

状态发生变化时 Backend 只记录一条不含连接地址的 `runtime health changed` 摘要，便于从容器日志确认是数据库、协调器还是 Worker 先失效，不会按每次健康轮询重复刷屏。

业务接口遇到未知数据库、Redis、存储、解密或配置错误时，公共响应只显示可执行的通用说明和服务端生成的“请求编号”，响应头同时带 `X-Request-ID`。把这个编号交给管理员即可关联同一条 Backend 访问日志和内部错误日志；不要要求用户提供 Cookie、API Key、完整请求正文或供应商密钥。服务器上可按编号检索：

```bash
docker compose --env-file .env -f docker-compose.deploy.yml logs backend | grep 'request_id=这里替换为请求编号'
```

访问日志不保存查询参数或请求头，因此 OAuth code、签名资源参数、Cookie 和 Authorization 不应进入常规请求行；公开画布分享 Token 也会替换成路由占位符。明确的参数/权限等 4xx 业务提示以及 524 等供应商费用风险仍会原样保留，避免脱敏后丢失处置依据。若同一请求没有对应编号、响应暴露内部路径，或日志出现凭据，应视为安全回归并立即隔离日志、轮换受影响密钥。

如果只想保留 503 的诊断正文，不要给 curl 加 `-f`：

```bash
curl -sS -w '\nHTTP %{http_code}\n' http://127.0.0.1:3000/api/health
```

同时在页面检查：

- “管理后台 → 数据概览”：活跃、调用和成本趋势；
- “请求明细”：失败率、上游状态、供应商任务 ID 和费用；
- 在线 Agent 请求的 `Operation` 应显示 `canvas_agent`，同一用户消息的每一轮都是独立记录；
- “任务”：长期排队、运行超时、失败和待核对计费；
- “资源与策略”：配额、并发和熔断是否合理；
- PostgreSQL、后端数据卷和 OSS 的剩余空间。

日志中不得长期保留 API Key、Cookie 或 Authorization。发现疑似泄露时，应先隔离日志访问，再轮换受影响密钥。

## 十、任务与计费恢复手册

### 1. 先区分失败类型

| 情况 | 风险 | 处理 |
| --- | --- | --- |
| 请求尚未发出就失败 | 通常未产生上游费用 | 修正配置后重试 |
| 上游明确返回失败 | 通常可退款 | 核对账本后修改输入或重试 |
| 上游 408、499、除 501 外的 5xx、读取中断或响应超限 | 上游可能已经执行并收费，不能因拿到错误响应就认定未调用 | 系统订单进入待核对；禁止立即重试，先查询原任务和供应商账单 |
| 409 同一请求标识已使用 | 重复请求已经被平台拦截，本次未再次调用供应商 | 查原计费订单和请求明细，不要换键绕过 |
| 内容审核失败 | 原输入不可继续 | 修改提示词后新建任务 |
| 失败/取消且有供应商任务 ID | 结果可能仍可恢复 | 使用“手动查询任务” |
| 视频已恢复但积分待核对 | 结果成功、结算异常 | 保留结果，管理员处理积分，不重复生成 |
| Backend 重启或 Worker 中断且没有可查询供应商任务 ID | 原供应商请求可能已经发出，自动恢复会变成第二次调用 | 系统终止为失败并阻止自动重放；先核对账单，结清待核对订单后再由用户明确重试 |

任务页、会话失败消息、计费备注和“请求明细”使用同一公开错误边界。上游 400/422 等明确拒绝只展示经过过滤的结构化短错误码与消息，不保存完整响应正文；408、499 和除 501 外的 5xx 只保留费用风险和处置提示。数据库、Redis、网络 URL、文件路径、密钥片段与结算底层错误只进入 Backend 日志。若页面只显示“内部错误”或“底层诊断仅记录于 Backend 日志”，请用任务 ID、订单 ID、请求时间和请求明细定位同一条服务端日志，不要要求用户复制密钥或反复重试来复现。

“请求明细”和运营分析 CSV 可能包含供应商错误、模型名和供应商任务 ID 等外部文本。导出时会给可能被 Excel 解释为公式的单元格增加文本前缀，包括 `= + - @` 以及前导控制或 Unicode 格式字符；规范负数仍保持数值。看到单元格以单引号保护是预期安全行为，不要批量删除前缀后重新打开文件。导出任一行或最终缓冲写入失败时接口会整体失败，不会把半截审计文件提示为下载成功。

### 2. 用户恢复

用户打开“任务 → 详情 → 手动查询任务”。系统只允许查询失败或已取消的视频任务，并复用当前计费尝试的供应商任务 ID。

如果上游仍在处理，页面会显示供应商状态；等待后再查。如果已经成功，系统会保存结果、恢复任务、尝试登记项目产物、结算积分并同步画布。

供应商一次返回多张图或多段媒体时，Backend 会先校验全批内容和额度，再逐个落盘。资源以任务、当前计费尝试和结果路径建立幂等身份：同一次视频人工查询或 Worker 恢复会复用摘要一致的已保存资源，不会因第一次只完成半批而重复创建前半批；用户明确确认的新付费重试使用新的尝试身份，不会误显示旧媒体。即使中途某个对象写入失败，任务也会保存“已完成资源引用 + 未完成内联正文 + pending 对象”的恢复检查点。如果任务显示“结果检查点已保存，但媒体持久化、会话或画布交付尚未完成”，点击“恢复已保存结果”只续写本地对象并提交本地交付，不访问供应商或创建新订单；长恢复会持续续租，租约丢失后停止下一个对象并提示刷新。人工查询上游视频已经确认成功、但本地 OSS 又失败时，也会切换到相同的本地恢复入口，而不是要求重新创建视频任务。恢复后若积分仍显示待核对，再由管理员按原订单结算。后端会拒绝对此类任务直接付费重试。

任务结果和计费已经成功，但项目步骤仍未推进时，不要重新生成。重新打开对应项目详情，Backend 会限量扫描当前项目及其关联画布中“成功但尚未登记”的任务，并按任务与步骤唯一键补登记；重复刷新不会重复增加项目或工作流修订号。若仍未恢复，按任务 ID 检查 Backend 日志中的 `reconcile project workflow output failed`，重点核对任务所属画布是否仍关联该项目、工作流步骤是否存在，以及数据库事务是否可写。

### 3. Worker 重启、panic 与 Redis 槽位

数据库任务租约每 15 秒续期一次，失效后约 45 秒才允许另一 Worker 领取。重新领取时系统会区分可证明安全的恢复路径：计费订单仍为 `reserved`，或新状态明确停在 `pending/preflight`，都能证明供应商请求尚未发出，可以继续；已经保存供应商任务 ID 的异步视频只查询原任务；`dispatched`、旧版模糊状态及其他无任务 ID 请求一律终止为“中断任务未自动重放”，系统订单进入待核对。这个保守失败是为了阻止 Backend 重启后把同一任务再次发给供应商。

首轮生成和一次已授权的分镜结构修复在真正请求供应商前，都会用数据库事务确认当前 Worker 租约仍未过期、写入任务阶段并创建调用前审计日志。新尝试先从 `pending` 进入 `preflight`；完成并发槽位等待、DNS 和请求构造后，HTTP 建连前还要用同一租约把状态原子改为 `dispatched`。任何一步失败都不会发送该次请求。分镜第二次结构修复会追加审计，但必须保留首轮已经 `dispatched` 的事实。无平台订单的个人渠道或测活任务只有持久状态明确为 `pending/preflight` 时才能在中断后安全接管；`dispatched`、旧版 `prepared` 及升级前空值都按可能已经调用处理。若任务页长期停在“后端接管任务”，先检查数据库写入与 Worker 日志；不要绕过原任务手工补发。

单个任务发生 panic 时，Worker 会在任务边界恢复，Backend 进程继续服务。若订单仍为 `reserved`，或订单虽为 `running` 但任务状态仍明确停在 `pending/preflight`，系统按供应商未调用退款；已经 `dispatched`、状态不明确或订单为 `uncertain` 时保持费用待核对。panic 类型和堆栈只写 Backend 日志，任务页只显示安全处置说明。

PostgreSQL 多实例通过 Redis 维护全局 Worker 并发。每个运行任务持有 2 分钟槽位并每 30 秒续租，短任务或探针不能缩短已有 Redis Key 的剩余 TTL。首次续租失败时，`/api/health` 的 `worker` 就会失败，受影响实例立即暂停领取新任务并写入任务日志；如果 Redis 在槽位到期前恢复，续租成功后会自动恢复健康与调度。槽位最终过期也不会粗暴取消当前供应商请求，实例会保持暂停直到原任务结束。此时不要用重启或手工重试“修复”健康状态，应先恢复 Redis、观察原任务和供应商账单；任务结束后实例会自动清理本地异常状态。

### 4. 取消不是供应商撤回

- 排队任务使用带状态条件的终态更新；只有确认仍在排队时才按“上游尚未调用”退款。若状态已经切到运行中，继续按运行中取消处理。
- 运行中任务不再一律视为已经调用供应商：取消事务会先尝试只在 `pending/preflight` 状态抢占终态，并与 HTTP 发送前的 `dispatched` 检查点竞争同一任务行。取消先赢时可以确认未建连并退回预留积分；发送检查点先赢、旧状态不明确或此前已有调用时，才终止本地上下文并把平台计费标为待核对。任务错误说明会持久化对应边界，用户端必须按提示处理。
- 取消已经成功后，即使冻结积分退回、计费待核对标记或风险说明保存失败，接口也不能伪装成“取消失败”诱导用户再次操作；系统会保留管理员核对提示和错误日志。
- 画布自动取消使用 30 秒控制请求时限；写响应丢失后必须读回原任务。确认取消或任务已失败才解除本地等待；任务已成功时引导恢复原结果，仍在活动或读回失败时标记状态/费用不确定。取消确认期间生成入口保持锁定，不能先恢复为空闲态。
- 生成入口同时检查节点持久化的 `taskId`、任务状态和节点回填状态；浏览器内存中的 `runningNodeId` 丢失或页面刷新不能解除排队/运行任务锁。核心生成函数也执行相同校验，不能只依赖按钮禁用。
- 服务端按用户、画布、节点、任务类型和操作生成活动请求键，并由数据库部分唯一索引兜底。多标签页、双击、脚本直调或多个 Web 实例并发命中同一操作时返回原任务 ID，不产生第二张订单；不同节点或不同操作仍可正常并行。
- 同步系统渠道的付费 POST 强制要求 `X-Idempotency-Key`。在线 Agent 以“会话、用户消息预算记录、模型轮次”生成稳定键；后端先按当前用户和键查询原订单，再等待渠道槽位，最终写入仍受数据库唯一索引保护。顺序或并发重复都返回 409，不会创建第二张订单、冻结流水或供应商调用。该代理不保存完整模型响应，因此 409 不能用于取回正文；管理员应根据原订单状态处理，不能让客户端自动换键补发。
- 影视 Agent 创建使用浏览器随机请求键和数据库永久唯一索引；Web 在 POST 前强制把请求键、提示词、原画布 ID 和 SHA-256 配置指纹写入 LocalForage，明文 API Key 不进入画布或后端同步数据。响应丢失或页面刷新后，只有原画布且渠道、模型、凭据版本等配置一致时才以原键恢复；配置变化会暂停补发，导入或复制的画布不会自动接管。若进程在会话、首条消息或任务之间中断，恢复路径使用固定消息 ID 和按会话计算的活动任务键补齐，只允许一张计费订单。
- 影视任务失败或取消时，任务终态、会话失败状态和以任务 ID 为主键的失败消息在同一数据库事务中提交；重复执行只更新原消息。会话查询还会修复旧版遗留的 `active` 会话，但只在对应任务当前仍为失败/取消时条件更新，不能覆盖已经重新入队的任务。
- 节点和批次的显式单项取消在收到后台终态后，只按任务 ID 停止对应轮询。共享批次控制器不得因此中断其他任务，也不得由轮询中止监听器再发送第二次取消请求。
- 管理员应以任务终态、当前计费订单、API 请求日志和供应商账单共同判断费用，不能只根据浏览器是否停止等待作结论。

### 5. 管理员恢复

进入“管理后台 → 请求明细”：

1. 筛选目标用户、渠道、模型或失败状态；
2. 打开当前请求详情；
3. 确认任务 ID、供应商任务 ID、计费订单和请求时间属于同一次尝试；
4. 点击“查询并恢复任务”；
5. 记录上游状态、恢复结果和积分结算结论。

系统会拒绝用历史重试日志覆盖当前任务，也会拒绝恢复已退款任务。

计费判定以“请求是否可能已经到达并执行”而不是只看 HTTP 是否为 2xx：上游 408、499、500、502、503、504、524 以及其他除 501 外的 5xx 都属于状态不确定；响应体读取中断或超过平台上限同样如此。501 明确表示接口未实现，可由文本兼容层切换路径；400、401、403、404、422、429 等明确拒绝可按失败退款。注意区分 Backend 自己在等待渠道槽位、读取请求体或构造上游请求阶段返回的 504：只有正文同时明确写明“调用供应商前、尚未调用/未发出上游请求”时，才可判定没有上游费用。

正常完成遵循“先写 API 请求日志，再结算积分”。如果上游已经完整返回，但请求日志或积分结算写入失败，系统不会把该正文作为成功结果交给 Agent 继续下一轮；非流式请求返回明确错误，SSE 会在原连接末尾追加错误事件，订单进入待核对。待核对是人工边界：普通 Worker 或同步代理即使迟到拿到成功或拒绝结果，也不能自动把它改成已结算或已退款；只有管理员根据供应商账单核对，或使用能够确认原上游任务状态的手动恢复入口后，才能处理终态。

### 6. 什么时候才能重新生成

必须同时满足：

- 原供应商任务已确认失败、不可查询或确实不需要；
- 当前计费订单不是保留、执行中或待核对；
- 用户理解新的上游任务可能再次收费；
- 内容审核失败已经修改提示词；
- 当前画布没有因为同步延迟而漏显示一个其实已成功的结果。

任务中心对所有重试都会再次显示费用确认。画布单节点、批量镜头和脚本分镜虽然会创建新任务 ID，也必须提交旧任务 ID；后端会重新验证旧任务归属、终态和当前计费订单，并要求显式携带 `confirmNewProviderRequest: true`。旧任务已成功、仍在活动、计费待核对、来源画布不一致或缺少确认时一律拒绝创建。重试与普通任务创建共享频率限制，新任务输入和任务日志会保留来源任务与用户确认事实。原任务重新入队时，新计费预留、Agent 会话恢复和确认日志在同一数据库事务中提交；日志或会话写入失败会连同积分预留一起回滚，不能出现“接口报错但任务其实已重试”的半成功状态。

### 7. 分镜 JSON 修复如何计费和审计

画布分镜、任务页 Agent 分镜与在线画布助手共用同一结构校验链路。每个任务先发送一次文本请求；只有任务创建输入明确携带 `allowPaidStructureRepair: true`，且首轮已经返回但无法规范化为合法分镜时，后端才允许再发送一次 `repair` 请求。未授权时任务会明确失败，并在日志中写明“未发起额外修复请求”。

这项授权的边界是“一次任务最多两次文本调用”，不是无限重试：第二轮仍不合法时直接失败，不得有第三次请求。524、连接中断、读取失败和响应状态不确定不会触发结构修复，因为原请求可能仍在执行并计费。

分镜请求强制从 `stream=true` 开始，但测活只作为管理员诊断和费用确认提示，不是创建前的用户授权证明。系统渠道仍读取模型目录，自定义渠道可提交当前用户的探针任务 ID供审计；未测活、过期、配置变化、SSE 疑似缓冲、非流式或失败状态都允许普通用户在明确确认后尝试，真实请求的协议完整性和费用边界负责终止不安全结果。官方 Kimi/Moonshot Chat 结构化分镜会同时发送 `response_format: {"type":"json_object"}`；K3-LS、K2.7 Code/K2.6 等已知兼容别名和普通兼容网关不会收到该供应商扩展，只使用结构化提示词；无论是否启用 JSON Mode，后端仍必须进行本地结构校验。若渠道明确表示不支持流式，系统直接失败并说明“未发起第二次非流式请求”；供应商后来改成只返回单包 SSE、完整 JSON、524 或损坏流时，本任务按费用边界结束并更新管理员诊断，普通用户的下一次调用仍需显式确认。

核对费用时同时查看：

- API 请求日志中的任务 ID 与请求类型；第二次结构修复必须标记为 `repair`；
- 任务日志中的首轮校验摘要、修复开始和修复完成记录；
- 任务成功结果中的 `structureRepairUsed`；为 `true` 时代表实际发起过第二次调用；
- 自定义 API Key 的供应商账单，或系统渠道运营方的上游账单。系统渠道用户仍按当前任务积分价格结算，但不代表平台上游只收到一次请求。

重试分镜任务会创建一轮全新的生成尝试，并保留原任务对一次结构修复的授权，因此理论上又可能产生一至两次供应商调用。任务中心必须再次显示费用确认，管理员应先核对上一轮是否存在 524 或未结清费用。

## 十一、备份策略

### 1. 必须备份的对象

| 对象 | 为什么必须备份 |
| --- | --- |
| PostgreSQL 或完整 SQLite 数据目录 | 用户、项目、任务、计费、渠道、审计和资源索引 |
| 后端 `/data` | 上传资源、媒体、本地文件和 `.settings-key` |
| `.env` | 数据库连接、路径、端口和部署参数 |
| OSS Bucket | 实际远端媒体对象 |
| 用户关键画布 ZIP | 浏览器降级缓存和可移植项目备份 |
| 发布版本、镜像摘要和迁移前代码 | 确保能在相同版本恢复 |

Redis 主要保存协调状态，不应作为项目和计费的唯一备份来源。恢复时通常让 Redis 在正确数据库状态上重新建立运行状态，比恢复过期锁和租约更安全。

服务器备份不会自动包含每个用户浏览器里的自定义 API Key、未同步本地缓存或浏览器偏好。用户应把密钥保存在独立密码管理器中，并定期导出关键画布；恢复后按需重新填写渠道密钥。

### 2. PostgreSQL 部署备份示例

在维护窗口中先暂停新任务，并同时检查任务中心、请求明细和供应商后台。不能只看页面上是否有人操作：正在运行或状态不确定的供应商请求被中断后，可能继续计费却无法取回结果。

源码部署随仓库提供脚本，镜像安装器也会从显式的同版本 `BACKUP_SCRIPT_URL` 保存同一文件。它必须收到人工确认，同时会直接查询 PostgreSQL；发现任何 `queued` / `running` 任务，或仍为 `reserved` / `running` 的系统渠道计费订单，都会在停止 Backend 前退出：

```bash
cd /opt/mingwant-studio
sudo env CONFIRM_NO_ACTIVE_TASKS=YES bash ./scripts/backup-server.sh
```

脚本的安全边界：

- 同一安装目录只允许一个备份进程；遗留 `.backup-server.lock` 时不会猜测并删除。
- 先记录 Web、Backend 是否运行，再暂停 Web 公开入口、默认等待 5 秒让已进入 Backend 的短请求收敛，第二次确认数据库没有活动任务或执行中订单，最后才暂停 Backend；退出和常见中断都会尽力恢复备份前真正运行的服务，不会把原本停用的服务擅自启动。个人自定义渠道的同步调用没有平台计费订单，因此人工确认仍必须覆盖 Backend 请求日志和供应商后台，数据库计数与短暂等待都不能替代这一步。
- PostgreSQL 使用 custom 格式转储，并立即用 `pg_restore --list` 检查归档可读性；Backend `/data` 以 Docker archive 模式复制并记录 UID、GID 和权限，必须包含真实普通文件 `.settings-key`，出现缺失或符号链接时拒绝生成恢复点。脚本要求通过 `sudo` 运行，否则不能可靠保留容器文件属主。
- 同一目录保存 `.env`、Compose 文件、版本、Git commit、实际镜像摘要、服务状态、PostgreSQL 转储、Backend 数据和 `SHA256SUMS`；完成前目录名带 `.incomplete`，任一步失败都会保留现场而不会伪装成完整备份。
- 默认输出到 `<INSTALL_DIR>/backups/<UTC 时间>`（默认安装目录即 `/opt/mingwant-studio`）。输出目录权限会收紧，但其中仍有明文密钥和业务数据，必须再加密、限制访问并转移到独立介质。
- Redis 协调状态和 OSS 对象不会进入这个目录。Redis 应从正确数据库状态重建，OSS 必须使用 Bucket 版本控制或独立复制策略。

自定义存储位置和可识别标签：

```bash
sudo env \
  CONFIRM_NO_ACTIVE_TASKS=YES \
  BACKUP_ROOT=/srv/secure-backups/mingwant-studio \
  BACKUP_LABEL=before-v1.2.3 \
  bash ./scripts/backup-server.sh
```

复制或恢复前先在备份目录验证：

```bash
sha256sum --check SHA256SUMS
```

脚本会拒绝把 `BACKUP_ROOT` 放进 Backend `/data` 的宿主机来源目录，避免递归复制。如果进程被 `kill -9`、宿主机断电或 Docker 本身崩溃，Shell 无法执行恢复钩子；此时先结合 `.incomplete` 目录中的 `service-state.txt` 检查并恢复原服务，再确认没有备份进程后手工移除空的 `.backup-server.lock`。未完成目录不能作为恢复点。

如果使用宿主机绑定目录，可由基础设施快照替代 `compose cp`，但仍要在一致的维护窗口执行，并确认快照包含隐藏文件 `.settings-key`。

### 3. SQLite 本地备份

先停止后端，再复制整个 `CANVAS_BACKEND_DATA_DIR`。不要只复制 `open_ai_canvas.db`：WAL、上传目录、媒体和 `.settings-key` 都属于同一套数据。恢复时也应整体恢复到同一路径。

### 4. OSS 备份

- 开启 Bucket 版本控制或使用供应商复制策略；
- 定期导出对象清单并与数据库资源索引比对；
- 保存 Bucket、Region、Endpoint、路径前缀和密钥版本记录；
- 删除业务记录前先确定远端对象保留、归档或清理规则；
- 不把“数据库中还有 URL”误认为对象本身已经备份。

## 十二、恢复演练

恢复优先在隔离的新环境进行，不直接覆盖唯一生产实例。

1. 在备份目录执行 `sha256sum --check SHA256SUMS`；任一文件不匹配都停止恢复并重新取得可信副本。
2. 准备与 `MANIFEST.txt` 对应的代码版本或镜像摘要。
3. 创建新的空 PostgreSQL 数据库和新的持久化卷。
4. 从 `deployment.env` 恢复必要配置，重新确认域名和端口，避免隔离环境连接真实生产上游。
5. 在 Backend 停止且目标卷为空时，以保留 UID/GID 的 archive 模式将 `backend-data/.` 完整放回 `/data`；对照 `backend-data.metadata` 和 `backend-data-settings-key.stat` 确认 `.settings-key` 的属主与权限，没有额外嵌套一层 `backend-data`。
6. 对空数据库执行：

```bash
docker compose --env-file .env -f docker-compose.deploy.yml exec -T postgres sh -c 'pg_restore --exit-on-error --no-owner -U "$POSTGRES_USER" -d "$POSTGRES_DB"' < postgres.dump
```

7. 启动后端与 Web。
8. 验证管理员登录、项目数量、画布、素材、任务、账本、OSS 读取和历史密文解密。
9. 如果准备了不会转发到真实供应商的自建 mock/沙箱渠道，用它执行一次最小任务；没有这种渠道时不要把恢复演练误当成免费测活，也不要为了验收盲目调用真实计费模型。
10. 记录恢复耗时、缺失数据和修正项。

不要对包含现有数据的目标数据库直接运行恢复命令。需要覆盖时，应先明确目标、完成独立备份并由负责人批准。

## 十三、版本更新

### 1. 更新前门禁

- 阅读当前版本和目标版本的 `CHANGELOG.md`；
- 检查 `docs/content/docs/pending-test.mdx`；
- 确认没有正在执行且不能中断的任务；
- 确认 `.env` 中容器停机宽限至少比 Backend 排空时长多 1 分钟，且排空时长覆盖当前最长任务/同步中转策略；
- 完成数据库、后端数据、OSS 和 `.env` 备份；
- 记录当前 Git commit、镜像摘要、数据库版本和恢复点；
- 在预发布环境先完成相同升级。

后端启动会执行 GORM `AutoMigrate`。即使没有手写迁移文件，数据库结构仍可能前向变化，因此升级前备份不可省略，旧版本也不保证能直接读取升级后的数据库。

### 2. 源码部署更新

安装脚本只在部署工作区没有未提交代码改动时执行快进更新。可以重新运行原安装命令；脚本会 `git pull --ff-only`、重建镜像并等待服务健康。

如果手工维护：

```bash
cd /opt/mingwant-studio
git status --short
git fetch origin --tags
git log --oneline HEAD..origin/main
git pull --ff-only origin main
docker compose --env-file .env -f docker-compose.deploy.yml -f docker-compose.build.yml build backend web
docker compose --env-file .env -f docker-compose.deploy.yml -f docker-compose.build.yml up -d --remove-orphans --wait --wait-timeout 600
```

工作区有本地改动时不要强制覆盖，应先确认这些改动属于哪个发布版本。

### 3. 镜像部署更新

使用明确的新版本重新运行镜像安装脚本。脚本会安全更新 `.env` 中两个镜像地址，保留其他数据库配置，并从同一版本的 `COMPOSE_URL` 与 `BACKUP_SCRIPT_URL` 更新部署文件，然后拉取并启动服务。

升级后检查实际运行镜像摘要，不要只看标签文本。

### 4. 同步上游项目

上游 `ddcat-ai/open-ai-canvas` 更新时，不应直接在生产部署目录合并。先在开发仓库进行只读比较：

如果尚未配置上游远端，先执行一次 `git remote add upstream https://github.com/ddcat-ai/open-ai-canvas.git`；已经存在时不要重复添加。

```bash
git remote get-url upstream
git fetch upstream --tags
git log --left-right --cherry-pick --oneline HEAD...upstream/main
git diff --stat HEAD..upstream/main
```

然后在独立分支整合：

```bash
git switch -c codex/upstream-目标版本
git merge --no-commit --no-ff upstream/main
```

## 十四、常见故障

| 故障 | 可能原因 | 处理 |
| --- | --- | --- |
| 所有 API 失败 | 后端未启动、Web 代理错误、反向代理未保留 Host | 检查 `/api/health`、容器状态和代理头 |
| 容器是 Up 但 `/api/health` 为 503 | 数据库、Redis/协调器或 Worker 调度已经失效 | 查看响应中的失败组件和 Backend 日志；恢复依赖后确认三项转为 `ok`，不要靠重启 Web 掩盖问题 |
| Backend 因 `CANVAS_CORS_ORIGINS` 拒绝启动 | 使用了 `*`、路径、查询参数、账号信息或非 HTTP(S) 来源 | 改为逗号分隔的精确 `https://主机[:端口]`；本地跨端口也逐项填写 |
| 返回“不允许的跨域来源” | 外部域名、Host 或 `CANVAS_CORS_ORIGINS` 不一致 | 保持同源，或只添加精确 HTTPS 来源 |
| 退出后提示服务端会话撤销失败 | 浏览器 Cookie 已过期，但数据库删除会话失败 | 不要忽略提示；检查 Backend 与数据库，按用户撤销剩余会话并排查故障 |
| 登录后数据为空，或本地脚本提示 Compose 项目标识变化 | 数据库、数据目录、仓库目录名或 `COMPOSE_PROJECT_NAME` 变化 | 停止写入，恢复原项目标识并找回原 `.env`、卷或路径；不要删除标识文件后继续注册 |
| 后端启动提示 PostgreSQL 缺少 `DATABASE_URL` | 驱动设为 PostgreSQL 但连接未配置 | 恢复正确 `.env`，不要回退到新的 SQLite |
| PostgreSQL 多实例提示缺少 Redis | `REDIS_URL` 未配置 | 配置内部 Redis 并检查连通性 |
| OSS 密钥无法解密 | `.settings-key` 丢失或恢复错数据目录 | 恢复与数据库同一备份集的 `.settings-key` |
| 模型列表为空 | 上游不支持 `/models`、Key 或 Base URL 错误 | 手工配置模型并按真实协议测试 |
| 浏览器出现第三方供应商 CORS，或媒体请求直接指向供应商域名 | Web 镜像或缓存过旧，或自定义部署绕过后端任务边界 | 检查媒体创建只访问本站任务 API，在线 Agent/模型目录只访问本站 `/api/ai/*`；更新 Web 并清缓存，不要放宽供应商 CORS |
| 渠道连续失败 | 上游不可用或已触发熔断 | 停止重试，修复上游后等待熔断恢复 |
| 视频长时间运行 | 正常异步轮询、供应商限流或上游卡住 | 查看任务日志和供应商状态，不创建重复任务 |
| 文本请求返回 524 | 供应商网关在模型完成前断开，任务可能仍在计费 | 查看测活与 API 日志是否使用流式；524 不会自动重试，先到供应商后台核对后再处理 |
| 更新或停止 Backend 后在途请求中断 | 使用了 `docker kill`/`kill -9`，容器宽限短于应用排空，或任务超过配置窗口 | 先核对供应商和订单，禁止立即重试；恢复 `CANVAS_SHUTDOWN_DRAIN_TIMEOUT < CANVAS_CONTAINER_STOP_GRACE_PERIOD`，再用普通 Compose stop/up 流程 |
| 任务提示“生成请求无法安全序列化” | 内部请求结构含无法编码为 JSON 的值 | 本次在建连前停止，供应商未被调用且预留积分应退回；按任务 ID 查 Backend 日志并修复请求构造，不要反复提交 |
| 供应商成功但结果持久化失败 | 结果或画布操作无法序列化，或数据库/存储写入失败 | 原供应商请求可能已计费，订单进入待核对；保留任务与订单并从 Backend 日志恢复原结果，禁止直接新建生成 |
| 任务成功但项目步骤未推进 | 任务结果已保存，但工作流产物登记事务中断，或任务所属画布已解除项目关联 | 先重新打开项目触发幂等补登记，不要重新生成；仍未恢复时按任务 ID 查 Backend 日志并核对画布归属与步骤是否存在 |
| 任务只显示“内部错误”或请求明细提示查看 Backend 日志 | 平台已隐藏数据库、Redis、URL、路径或密钥相关底层诊断 | 记录任务 ID、订单 ID、时间和渠道，在 Backend 日志中关联排查；不要让用户提交密钥，也不要仅凭公开短消息判断是否已调用供应商 |
| 图片、音频或视频任务等待超时 | 供应商可能仍在执行；异步视频可能已有可恢复任务 ID | 禁止立即重试；视频先手动查询原上游任务，其他媒体先核对供应商账单与平台订单。仅当错误明确证明未调用供应商时才可在退款后重新提交 |
| 在线 Agent 页面数分钟无增量 | 外层代理缓冲、部署仍是旧镜像，或供应商没有真正输出 SSE | 确认请求 `Operation=canvas_agent`、外层 `proxy_buffering off` 和 3600 秒超时；需要中断时用红色“停止”并核对费用，不要直接收起或刷新；供应商自身非流式接口需更换渠道 |
| 自定义渠道返回 2xx 后提示“响应无法完整交付” | 上游正文无效、响应超限、内容类型或 SSE 完整性不符合协议 | POST 模型请求可能已经执行和计费，禁止立即重试；先按请求编号查 Backend 日志并核对供应商。只有模型目录 GET 可按非计费配置错误处理 |
| 视频创建 524 后费用待核对 | 创建结果不确定 | 使用手动查询或管理员恢复，禁止立即重试 |
| 手动查询提示尚未到时间 | 上游仍在处理，或上一轮查询遇到暂态故障并进入退避 | 等待任务详情显示的时间；提前查询会在数据库抢占阶段返回 429，且不会访问供应商。不要用脚本循环点击或绕过退避 |
| 任务成功但画布没回填 | 浏览器或本地缓存同步失败 | 保留成功任务，重新同步画布，不重复收费生成 |
| 存储配额不足 | 文件、结构化数据或任务历史达到上限 | 检查配额和实际占用，先备份再制定清理方案 |

## 十五、事故处理最小流程

出现数据、计费或密钥事故时：

1. 停止新任务和相关写入，不急于重试。
2. 记录时间、用户、任务 ID、计费订单、请求日志和供应商任务 ID。
3. 保护当前数据库、日志、数据目录和容器状态快照。
4. 判断是上游生成、系统计费、资源保存、画布同步还是密钥泄露。
5. 只对当前任务和当前计费尝试做恢复，禁止使用历史日志覆盖。
6. 涉及密钥时立即限制访问并轮换受影响凭据。
7. 修复后在隔离环境复现，再恢复生产写入。
8. 将可执行的长期约束补入项目文档或 `AGENTS.md`。
